# Parnuan Software Engineer — Assignment 1

โปรเจกต์นี้เป็น Proof of Concept สำหรับแปลงข้อความการใช้เงินให้กลายเป็นรายการที่ผู้ใช้ตรวจสอบ แก้ไข และยืนยันได้ก่อนจบขั้นตอน

ผมตั้งใจทำให้ระบบเล็กและอ่านง่ายก่อน โดยให้เห็น flow หลักของผลิตภัณฑ์ชัดเจน ไม่ทำส่วนที่ยังไม่จำเป็นสำหรับโจทย์นี้ เช่น ระบบสมาชิก ฐานข้อมูล หรือการบันทึกถาวร

## ระบบนี้ทำอะไร

ผู้ใช้พิมพ์ข้อความธรรมดา เช่น

```text
ข้าวมันไก่ 50 น้ำเปล่า 7 แล้วก็ช้อปปิ้ง 500
```

ระบบจะแยกข้อความออกเป็นรายการ แสดงจำนวนเงิน หมวดหมู่ และวันเวลา จากนั้นผู้ใช้สามารถตรวจสอบ แก้ไข หรือลบรายการก่อนกดยืนยัน

ตัวอย่าง flow:

```text
พิมพ์ข้อความ
    ↓
ระบบแยกรายการ
    ↓
ผู้ใช้ตรวจสอบและแก้ไข
    ↓
ผู้ใช้ยืนยันรายการ
```

## วิธีติดตั้งและรัน

ต้องมี Node.js และ npm ในเครื่อง

```bash
npm install
npm run dev
```

จากนั้นเปิด [http://localhost:3000](http://localhost:3000)

คำสั่งตรวจสอบก่อนส่งงาน:

```bash
npm test
npm run build
```

## สิ่งที่ทำได้ในตอนนี้

- รับข้อความรายการใช้จ่าย 1 รายการหรือหลายรายการในข้อความเดียว
- แยกชื่อรายการและจำนวนเงินออกจากข้อความ
- รองรับจำนวนเงิน เช่น `10`, `10 บาท`, `10บาท`, `฿10.50` และ `1,000 บาท`
- แยกเวลาที่เขียนตรง ๆ เช่น `15:00`
- อ่านเวลาภาษาพูด เช่น `บ่าย 3`, `6 โมงเย็น` และ `เที่ยง`
- อ่านวันเวลา เช่น `เมื่อวานตอน 5 โมงครึ่ง`
- แสดงคำเตือนเมื่อข้อมูลกำกวม เช่น `6 โมง` ที่ยังไม่รู้ว่าเช้าหรือเย็น
- แก้รายละเอียด จำนวนเงิน หมวดหมู่ วันที่ และเวลาก่อนยืนยัน
- ลบรายการหรือล้างรายการทั้งหมดได้
- ล็อกข้อมูลหลังจากกดยืนยัน เพื่อป้องกันการแก้ไขโดยไม่ตั้งใจ
- แสดงยอดรวมในรูปแบบหน้ากระดาษคล้ายใบเสร็จ

## สิ่งที่ผมวิเคราะห์จากภาพตัวอย่าง

จากภาพ ผมเข้าใจพฤติกรรมของระบบเดิมดังนี้:

1. ข้อความหนึ่งข้อความสามารถสร้างรายการใช้จ่ายได้มากกว่าหนึ่งรายการ
2. แต่ละรายการมีชื่อ จำนวนเงิน หมวดหมู่ และวันเวลา
3. ระบบควรแสดงผลให้ผู้ใช้ตรวจสอบก่อน ไม่ควรบันทึกทันทีจากการเดาของระบบ
4. ผู้ใช้ควรแก้ไขหรือลบรายการที่ระบบแยกผิดได้
5. เมื่อผู้ใช้ตรวจสอบแล้วจึงกดยืนยันรายการ

ผมจึงออกแบบหน้าเว็บให้มีลักษณะเหมือนใบเสร็จ มีรายการและยอดรวมอยู่ในหน้าเดียว เพื่อให้ผู้ใช้เห็นผลลัพธ์ทั้งหมดได้เร็ว

## สมมติฐานที่ใช้

- จำนวนเงินในข้อความใช้เลขอารบิก เช่น `50` หรือ `1,000` ซึ่งเป็นรูปแบบที่เลือกใช้ในโปรเจกต์นี้
- ถ้าไม่เขียนเวลา ระบบใช้เวลาขณะที่รับข้อความ และแสดงคำเตือนว่าเวลานี้เป็นค่าเริ่มต้น
- ถ้าเวลายังตีความไม่ได้ ระบบจะไม่เดาเอง แต่แสดงคำเตือนให้ผู้ใช้ตรวจหรือแก้ไข
- หมวดหมู่เริ่มต้นมาจากคำสำคัญในชื่อรายการ เช่น `น้ำ` เป็นเครื่องดื่ม และ `ข้าว` เป็นอาหาร
- ข้อมูลใน Proof of Concept นี้อยู่ใน state ของหน้าเว็บและยังไม่บันทึกลงฐานข้อมูล

## การออกแบบทางเทคนิค

ผมแบ่งโค้ดเป็นสองส่วนหลักเพื่อให้แก้และทดสอบง่าย:

### 1. ตัวแยกข้อความ

ไฟล์ `lib/expense-parser.ts` รับข้อความแล้วคืนค่าเป็นรายการที่มีรูปแบบเดียวกันทุกครั้ง โดยใช้ regular expression และกฎเล็ก ๆ ที่อ่านตามได้

ลำดับการทำงานคือ:

1. ตรวจหาวันและเวลาจากข้อความ
2. ตัดส่วนวันเวลาออกจากข้อความที่จะใช้แยกรายการ
3. ค้นหาชื่อรายการที่อยู่ก่อนจำนวนเงิน
4. แปลงจำนวนเงินให้เป็นตัวเลขกลาง เช่น `1,000` เป็น `1000`
5. เลือกหมวดหมู่จากคำสำคัญ
6. ใส่คำเตือนถ้าข้อมูลไม่ชัดเจน
7. ตรวจรูปแบบผลลัพธ์ด้วย `transactionSchema` ก่อนส่งต่อ

ส่วนนี้ไม่มีการเรียก LLM เพราะโจทย์นี้สามารถทำ flow หลักด้วยกฎที่ชัดเจนก่อน ทำให้ผลลัพธ์ตรวจสอบได้เร็ว ไม่มีค่าใช้ API และรู้ได้ว่ากฎข้อไหนทำให้เกิดผลลัพธ์นั้น

### 2. หน้าตรวจสอบรายการ

ไฟล์ `components/receipt/receipt-page.tsx` ดูแล state ของข้อความ รายการ และสถานะการยืนยัน

- สถานะ `รอตรวจสอบ`: ผู้ใช้แก้ไขหรือลบรายการได้
- สถานะ `ยืนยันแล้ว`: รายการถูกล็อกและซ่อนปุ่มแก้ไข/ลบ
- การกด `เริ่มรายการใหม่` จะล้างรายการเดิมเพื่อเริ่มรอบใหม่

## รูปแบบข้อมูลรายการ

รายการหนึ่งรายการมีข้อมูลดังนี้:

| ฟิลด์ | ความหมาย |
| --- | --- |
| `id` | รหัสรายการชั่วคราว |
| `description` | ชื่อหรือรายละเอียดรายการ |
| `category` | หมวดหมู่ เช่น อาหาร หรือ เครื่องดื่ม |
| `amount` | จำนวนเงินในรูปตัวเลข |
| `date` | วันที่ในรูป `YYYY-MM-DD` |
| `time` | เวลาในรูป `HH:mm` หรือไม่มีค่า |
| `timeSource` | เวลามาจากข้อความ ค่าเริ่มต้น หรือเป็นกรณีกำกวม |
| `warnings` | คำเตือนที่ควรให้ผู้ใช้ตรวจ |
| `sourceText` | ข้อความส่วนที่ใช้สร้างรายการ |

การมี `warnings` และ `timeSource` ช่วยแยกให้เห็นว่าอะไรคือข้อมูลจากข้อความ และอะไรคือค่าที่ระบบเติมให้เอง

## การจัดการข้อมูลกำกวม

ระบบเลือกแสดงคำเตือนแทนการเดาในกรณีที่มีโอกาสทำให้ข้อมูลการเงินผิด เช่น:

- `6 โมง` ยังไม่ชัดว่าเป็น `06:00` หรือ `18:00`
- ไม่มีเวลาในข้อความ ระบบใช้เวลาที่รับข้อความเป็นค่าเริ่มต้นและแจ้งเตือน
- ไม่มีจำนวนเงิน ระบบจะไม่สร้างรายการที่ไม่สมบูรณ์
- เวลาแก้ไขเองต้องอยู่ในรูป `ชั่วโมง:นาที` เช่น `12:00`

แนวคิดคือให้ผู้ใช้เป็นคนตัดสินใจในจุดที่ระบบไม่มั่นใจ แทนการบันทึกข้อมูลผิดโดยไม่มีสัญญาณเตือน

## ข้อแลกเปลี่ยนของการออกแบบ

### เหตุผลที่เลือก Rule-based Parser

ข้อดีคือโค้ดสั้น อ่านตามได้ ทำงานเร็ว ไม่มีค่าใช้บริการ และเหมาะกับชุดตัวอย่างที่โจทย์ให้มา การแก้กฎทำได้จากฟังก์ชันที่เกี่ยวข้องโดยตรง

ข้อเสียคือไม่ครอบคลุมภาษาธรรมชาติทุกแบบ ถ้าผู้ใช้พิมพ์ประโยคซับซ้อนหรือใช้คำใหม่ที่ไม่มีอยู่ในกฎ ระบบอาจแยกรายการไม่ครบ

### เหตุผลที่เลือกทำ UI ก่อนฐานข้อมูล

โจทย์ต้องการพิสูจน์ flow ตั้งแต่ข้อความจนถึงการตรวจสอบ ผมจึงทำให้ผู้ตรวจเปิดเว็บแล้วเห็นพฤติกรรมได้ทันที ส่วนการเก็บข้อมูลถาวรเป็นงานที่ควรทำหลังจากรูปแบบรายการและ review flow ชัดเจนแล้ว

## กรณีที่ทดสอบแล้ว

ตัวอย่างหลักตามโจทย์:

1. รายการเดียว: `ข้าวมันไก่ 50`
2. หลายรายการ: `ข้าวมันไก่ 50 น้ำเปล่า 7 แล้วก็ช้อปปิ้ง 500`
3. มีเวลา: `เมื่อวานตอน 5 โมงครึ่ง ข้าวมันไก่ 50`

นอกจากนี้มีการทดสอบรูปแบบเวลา จำนวนเงินที่มีและไม่มีช่องว่าง เวลากำกวม และข้อความที่ไม่มีจำนวนเงิน รวมทั้งหมด 7 test cases ใน `lib/expense-parser.test.ts`

## ข้อจำกัดที่ทราบ

ตอนนี้ระบบยังมีขอบเขตเป็น Proof of Concept:

- ยังไม่มีฐานข้อมูลและการบันทึกถาวร
- ยังไม่มี API แยกสำหรับเรียก parser
- หมวดหมู่ใช้คำสำคัญ จึงอาจจัดคำที่ไม่เคยอยู่ในกฎเป็น `อื่น ๆ`
- ยังรองรับรูปแบบจำนวนเงินและเวลาตามกฎที่กำหนดไว้ ไม่ใช่ภาษาธรรมชาติทุกแบบ
- ยังไม่มีระบบผู้ใช้หลายคน
- การยืนยันในตอนนี้เป็นการเปลี่ยนสถานะบนหน้าเว็บ ยังไม่ได้ส่งข้อมูลไปบันทึกภายนอก

## ถ้ามีเวลาเพิ่มจะทำอะไรต่อ

ลำดับที่ผมจะทำต่อคือ:

1. เพิ่มชุดตัวอย่างภาษาไทยจริงและทดสอบให้ครอบคลุมมากขึ้น
2. แยก parser เป็นฟังก์ชันย่อยหรือโมดูลตามชนิดข้อมูล เพื่อเพิ่มกฎได้ง่าย
3. เพิ่ม confidence หรือระดับความมั่นใจให้แต่ละฟิลด์
4. เพิ่ม API และฐานข้อมูลเมื่อรูปแบบข้อมูลนิ่งแล้ว
5. เก็บประวัติการแก้ไขของผู้ใช้ เพื่อใช้เป็นข้อมูลสำหรับ Assignment 2

Assignment 2 จะทำต่อเป็นขอบเขตแยกจาก Assignment 1 โดยเริ่มจากข้อมูลการแก้ไขและการยืนยันของผู้ใช้ ไม่ทำให้โค้ดส่วนนี้ซับซ้อนเกินความจำเป็น

## การใช้เครื่องมือช่วย

ผมใช้เครื่องมือช่วยตรวจ syntax ระดมแนวทาง และช่วยคิดกรณีทดสอบบางส่วน แต่การเลือกขอบเขต โครงสร้างข้อมูล กฎการแยกข้อความ และการตรวจผลลัพธ์เป็นส่วนที่ผมทบทวนกับโค้ดจริงเอง

## เวลาที่ใช้

ใช้เวลาประมาณ 3–4 ชั่วโมง แบ่งคร่าว ๆ เป็น:

- วิเคราะห์ภาพและวาง flow: ประมาณ 30 นาที
- ทำ parser และกฎวันเวลา/จำนวนเงิน: ประมาณ 1 ชั่วโมง
- ทำหน้า UI สำหรับตรวจ แก้ไข และยืนยัน: ประมาณ 1 ชั่วโมง
- เขียน test, README และตรวจการทำงาน: ประมาณ 1 ชั่วโมง

## Git workflow

ผมแยกงานเป็น branch ตามฟีเจอร์และใช้ commit ที่สื่อความหมาย เช่น:

- `feature/amount-formats`
- `feature/review-all-fields`
- `feature/lock-confirmed-receipt`

แต่ละส่วนจะทดสอบและ push ให้ตรวจสอบก่อน แล้วจึงค่อย merge เข้า `main` เพื่อให้เห็นลำดับการพัฒนาและเหตุผลของแต่ละการเปลี่ยนแปลง
